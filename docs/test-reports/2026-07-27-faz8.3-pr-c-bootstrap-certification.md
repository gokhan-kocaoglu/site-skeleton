## Rollback fault-injection kanıtı

```
[bootstrap-transaction] PASS — transaction ortasında hata tam rollback üretir
```

Enjeksiyon export edilen `executeBootstrapPlan(root, plan, { onOperation })`
seam'inden yapılır — CLI'da failure flag'i, rollback atlama seçeneği veya debug
env değişkeni **yoktur**. Hata, en az bir `move` uygulandıktan sonra (plan
sonundan bir önceki operasyonda) tetiklenir. Rollback sonrası doğrulananlar:

- tüm dosya sha256'ları başlangıçla aynı (`diffHashTrees` → 0 fark),
- `git status` çıktısı başlangıçtakiyle birebir aynı,
- `SiteSkeleton/` canlı konumuna döndü, `_ARCHIVE/` kaldırıldı,
- üretilen `01_Projects/certified-demo/` kaldırıldı,
- `com/skeleton` geri geldi, `com/certifieddemo` kaldırıldı,
- manifest `mode=skeleton-dev`, `projectSlug` yok.

`git reset --hard`, `git clean`, `git restore .` veya otomatik stash
kullanılmaz; rollback yalnız planın dokunduğu yollarla sınırlıdır. Rollback'in
kendisi de hata verirse hem ilk hata hem rollback hatası raporlanır ve
fail-closed çıkılır.

## Post-CI Transaction Review Remediation

PR #27 ilk head SHA'sı **`afb2be87f3d9f9d7ac3d574f60b4eb5a1ed03262`** ile açıldı ve
uzak CI run **`30260499437`** üzerinde **7/7 check success** verdi. Buna rağmen
bağımsız kod incelemesi transactional rollback'te gerçek bir açık buldu — yeşil
CI'ın kapsamadığı bir yol.

### Bulgu

`applyOperation` içindeki `move` dalı journal kaydını `renameSync`'ten **önce**
yazıyordu:

```js
journal.push({ type: 'move', from: op.from, to: op.to });
renameSync(p(root, op.from), p(root, op.to));
```

`renameSync` başarısız olursa journal, hiç gerçekleşmemiş bir taşıma kaydı
içerir. Rollback ters sırada ilerlerken bu hayali kayda gelir, var olmayan
`to` yolunu `from`'a taşımaya çalışır, kendisi hata verir ve **unwind döngüsü
orada kesilir** — o noktaya kadar uygulanmış tüm replace ve move işlemleri
repository'de kalır. Yani "yarım dönüşüm bırakmaz" güvencesi, tam da en çok
gerektiği anda çalışmıyordu.

Plan doğrulaması bunu önleyemez: hedefin dolu olması plan üretimi ile
uygulama arasında (TOCTOU) da oluşabilir.

### Regresyon testi

`scripts/tests/bootstrap-transaction.mjs` içine yedinci senaryo eklendi:
**"move rename hatası önceki operasyonları tamamen geri alır"**.

Enjekte edilmiş `onOperation` istisnası KULLANILMAZ — gerçek bir `renameSync`
hatası üretilir: plan doğrulandıktan sonra ikinci Java move'unun **hedefi**
dolu bir dizinle işgal edilir. Kaynak yerinde kaldığı için önceki tüm
replace'ler ve ilk Java move başarıyla uygulanır; yalnız ikinci rename kırılır
(Windows'ta `EPERM`, Linux'ta `ENOTEMPTY`). Kaynağı silmek işe yaramazdı:
o dizindeki dosyalar daha erken bir replace yedeklemesinde okunuyor ve koşum
move'a hiç ulaşamıyordu.

Baseline, hedef işgal edildikten sonra ve execution başlamadan hemen önce
alınır. Doğrulananlar: `BootstrapError` atıldı · mesaj gerçek `rename` hatası
içeriyor · `rollback tamam` var · `GERİ ALMA DA BAŞARISIZ` **yok** · ilk Java
move geri alındı · tüm dosya hash'leri baseline ile aynı · `git status` aynı ·
manifest `skeleton-dev`'e döndü · engelleyen hedef rollback tarafından
silinmedi · transaction backup dizini kalmadı.
